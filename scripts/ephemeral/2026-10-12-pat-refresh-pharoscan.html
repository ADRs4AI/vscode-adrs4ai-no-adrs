Part 1 — Azure DevOps (powers vsce publish)

1 · Confirm the old token is dead

Is the revoked PAT already gone from the list?

Azure already auto-revoked vsce-publish-jlumbroso on 2026-10-11 (their own notification said so). This step is just making sure it's visibly gone, not still sitting there "revoked but present."

  1. Go to https://dev.azure.com/lumbroso — not portal.azure.com, that's a different Microsoft product and has bitten this project before.
  2. Click the user-settings icon, top right (gear-ish / person icon next to your avatar).
  3. Click Personal Access Tokens in the menu that opens.
  4. Find vsce-publish-jlumbroso in the list. It should show as revoked/expired. If it's still listed and NOT marked revoked, click it → Revoke yourself.

2 · Decision — name the new token

What should the new PAT be called?

Lean: A. Costs nothing, and the ADR (0045, QST-PAT-SCOPE) already assumes a dated name for the trail. Confidence: 90%. Falsifier: if some automation elsewhere matches on the exact string vsce-publish-jlumbroso and would break on a renamed token — not something I found in this repo, but you'd know if it exists elsewhere.

3 · Decision — scope (this is ADR-0045's QST-PAT-SCOPE)

How much access should the new token have?

The old token had Marketplace (Acquire + Manage), Identity (Read & Manage), and Packaging (Read/Write/Manage) — broader than anything this project's tooling actually uses. Only vsce publish/package/show/verify-pat run against it, and those only need Marketplace.

Lean: A. Nothing this project runs has ever exercised Identity or Packaging scope — checked the actual `vsce`/`ovsx` commands used throughout this repo's history. If something new genuinely needs broader access later, mint a second, separately-named token for that purpose — keeps each credential's blast radius legible from its name alone. Confidence: 85%. Falsifier: a future `vsce` subcommand this project hasn't used yet that needs Identity/Packaging — would show up as an explicit permission error, not a silent failure.

4 · Decision — expiration

Should the new token expire?

The old one had no expiration — lived until it leaked. Azure lets you set a bounded lifetime.

Lean: A, mildly. The cost of rotating just dropped to "fill out this page again," so the usual objection to expiring tokens (rotation is a chore) is weaker than it was. Confidence: 60% — genuinely a judgment call, not a correctness question.

5 · Create it

Generate the token with whatever you picked above

  1. Still in Personal Access Tokens, click + New Token.
  2. Name: whatever you picked in step 2.
  3. Organization: lumbroso.
  4. Expiration: whatever you picked in step 4.
  5. Scopes: whatever you picked in step 3 (if "Custom defined → Marketplace", tick Manage under the Marketplace row — not Acquire-only).
  6. Click Create. The value is shown exactly once — don't close the page yet.

6 · Store it — not here, not in any chat

Paste the value directly into .env

The token value never goes in this page, in a chat message, or in any file this project's extension or crew might ever commit. That's exactly how the last one leaked.
  1. Open /Users/jlumbroso/Programming/vscode-adrs-for-ai/.env directly in a plain text editor (not through this page, not by pasting into a chat).
  2. Find the line starting VSCE_PAT= and replace everything after the = with the new value.
  3. Save the file.

Once this is done, just tell me "Azure's set" — I'll run vsce verify-pat jlumbroso myself to confirm it's live. I never need to see the value.
